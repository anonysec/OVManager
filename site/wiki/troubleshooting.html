Troubleshooting

The symptoms people actually hit, each in the order worth checking. All of it runs from a shell on the panel server, so none of it depends on the panel being reachable.

I lost the panel URL (the /random-path/ part)

The panel hides behind a secret path, and requests without it get an empty 404 page. That is normal behaviour, not a crash.

The panel is served at / again. Set a new random path in Settings → General → Panel URL Path; tick "I saved the new URL" and the page redirects you to it. Prefixes that collide with real routes — api, assets, health, the subscription path — are rejected automatically.

From a native install, the equivalent is cd /opt/ovmanager && sudo uv run main.py --reset-urlpath. On Docker, run the same command inside the container, or check ovm status.

If ovm recovery still shows a URL you cannot reach, remember that /sub/... and /health are intentionally served without the prefix — subscription links have to be shareable and health checks have to keep working.

I forgot the owner password

The owner credential is a row in the panel's database, not a .env value. Reset it from the server; user data is untouched.

The interactive form asks for the new password twice, with hidden input. Both script forms restart the panel afterwards and wait for /health. The value is never echoed and never logged — it rides in the environment rather than in argv, because a command-line argument is visible in ps to every user on the box.

Placeholder-looking passwords (change-me, changeme, password123, admin123) are refused, exactly as the panel refuses them. The same reset is entry 2 of the sudo ovm recovery menu. Docker installs work the same way — ovm finds and restarts the container.

Login fails with "username or password is incorrect"

  • Caps lock, or a trailing space. Passwords are case-sensitive.
  • Five wrong tries in five minutes locks that username for five minutes, with both a per-IP and a per-user limit. Wait and retry — restarting the panel does not clear the lockout.
  • Still locked out with shell access? Use reset-password above.

The browser warns about the certificate

Expected with the self-signed default. The connection is encrypted; the browser just does not know who issued the certificate. Click Advanced, then Proceed. The warning disappears once you switch to Let's Encrypt with a real domain — see TLS certificates and ovm tls-status.

ovm status or ovm doctor call the panel unreachable

Rarely a certificate problem. The health probe deliberately pins the certificate recorded in .env (SSL_CERTFILE) and only falls back to unverified behaviour when it cannot read that file, so a healthy self-signed panel reads as healthy. The hostname is not checked on purpose: the installer's certificate carries the public IP as its common name and has no SANs, while the probe dials 127.0.0.1, so a name check would fail on a perfectly good panel.

Node stays red

Check in this order:

#Check
1 Address. Public IP or hostname of the node, not a 10.x/192.168.x address — unless panel and node share a private network.
2 Port. The service port (2083 by default), not the VPN port (1194).
3 API key. An exact copy with no extra spaces. It can only be regenerated by reinstalling the node with the same --name — then update the panel entry too.
4 TLS switch. It must match the node: selfsigned/le means on, none means off. A mismatch is a silent connection failure.
5 Name. The panel's node name must equal the node's --name exactly.
6 Firewall. 2083/tcp reachable from the panel. Cloud security groups are the usual culprit.

No node-down Telegram alert

  1. Bot set up. Token and owner ID saved in Settings → Bot, and Start tapped in the bot once — Telegram refuses messages from users who never started the chat.
  2. Toggle on. Settings → Alerts → "Node goes down or comes back".
  3. Wait a probe. Detection is transition-based on the five-minute collector, so allow up to about five minutes after the node actually went down.
  4. One message per outage. A still-down node is not re-alerted every five minutes: you get the down message once and a "back online" message on recovery.
  5. Deleted and re-added the node? Alerts key off the panel node entry, so re-adding it resets the "already alerted" state. That is expected.

If the bot itself was broken during the outage, a failed send is retried on the next tick — the alert arrives late, not never.

Subscription link shows localhost, or will not download

Subscription and download links are built from the address you opened the panel with. Always log in through the public URL. Opening the panel as http://localhost:2095/... through an SSH tunnel is the usual cause, and the links you copy then carry localhost.

Behind a proxy where the request host is wrong, pin it explicitly: set PUBLIC_URL=https://panel.example.com in .env, or pass OVM_PUBLIC_URL at install time, or set the base URL under Settings → Subscription Link, then restart the panel.

VPN connects but there is no internet

This is a node-side problem: IP forwarding and NAT.

  • Native installs handle it through the ovnode-nat service — check systemctl status ovnode-nat.
  • Docker handles it in the container entrypoint, which needs CAP_NET_ADMIN and /dev/net/tun mounted.
  • Verify sysctl net.ipv4.ip_forward is 1, and that no other firewall (nftables, a cloud security group) is blocking forwarding.

Installer errors

MessageWhat to do
Must run as root (sudo) Re-run with sudo.
systemd not found — native install needs it Use Docker mode (WSL, containers), or a full VM.
Port 80 is busy — Let's Encrypt standalone needs it Stop whatever listens on 80, or install with a self-signed certificate for now.
docker compose startup failed docker logs ovmanager — usually a busy port or no disk space.
No answer on /health journalctl -u ovmanager -f natively, or docker logs -f ovmanager; then ovm status.
No verified release file is available, or a checksum error The installer only accepts a verified release archive and its SHA-256 sidecar. If those artifacts are not published yet, nothing is wrong with your server — use a from-source install. On an older install that is stuck on a download error, re-bootstrap with the current raw one-liner and then run ovm update.

Starting over

The panel keeps its data on uninstall unless you purge, and a purge first takes a snapshot at /var/backups/panel-pre-purge-*.tar.gz. Node data in /var/lib/ovnode and /etc/openvpn likewise survives a reinstall — rename-safe only if you keep the same --name.
