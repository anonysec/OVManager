Traffic limits

Quotas are in GB per user, the panel counts them once every five minutes, and the numbers are designed so a restart or a dropped session can never bill anyone twice.

Setting a limit

  • Traffic quota (GB) on the user — empty means unlimited.
  • Default traffic (GB) under Settings → Defaults — what a new user gets when you do not override it.
  • Add traffic (GB) on an existing user — added to their current quota. Leave it at 0 to keep the quota unchanged.

How usage is collected

Every five minutes the panel asks each node for /sync/usage. The node answers with a lifetime total per user: bytes banked when sessions ended, plus bytes still flowing in live sessions.

The panel remembers the last number it saw per node and adds only the increase to that user's used counter. That single design choice is what makes the accounting survive real life:

  • A short session that starts and ends between two polls is still counted, because the node's total only ever grows.
  • A disconnect, a node restart or a reconnect does not re-count bytes already banked.
  • A total that shrinks — a node rebuilt, or counters lost — bills zero instead of a negative or an absurd number.

One commit per tick

A node's whole payload is processed and then stored with a single database commit per tick. Each individual user write is conditional — it only applies if the row still holds the value the panel read. If you reset or delete that user in the browser at the same moment, the stale update becomes a no-op instead of overwriting your change.

What enforcement does

WhenWhat happens
Quota crossed Enforced immediately after that five-minute tick — not at the next sweep.
Expiry date passed Caught by a separate ten-minute sweep, which covers the expiry-only case.
80% of quota or more Shows as a warning, and feeds the owner's Telegram summary if that notification is on.
Over quota The user is disabled on the next check.

Device limits are enforced on the node

The device limit is not policed by the panel asking politely. The panel pushes max_logins to every node and the node enforces it at connect time:

  • 1 — a new connection takes over the existing one.
  • N — the N+1th simultaneous connection is rejected.
  • 0 — unlimited.

Enforcing at connect time is what makes the limit real: the panel only aggregates session counts, and can disconnect sessions it can see.

The live view, and why it does not hammer your nodes

The dashboard has a live view. A background collector polls the nodes every 10 seconds while a browser has the stream open, and backs off to every 5 minutes when nobody is watching. Request handlers read that in-memory snapshot rather than fanning out to every node per request, so one dead node can never stall the user list.

Traffic history is charted over the last 14 days, which is a good place to spot the user who is about to hit their quota.

Notifications

With the Telegram bot configured, the owner gets a daily summary covering users expiring within three days and users out of traffic, plus quota warnings from 80% up. Each of those is a separate toggle under Settings → Alerts, so you can keep the quota warnings and drop the rest.
